📋 [01단계] 기획 및 요구사항 구체화 실전 플레이북 ​

단계 요약: 한두 줄의 추상적인 비즈니스 아이디어나 기능 요청을 AI와 대화형으로 상호작용하여 누락 없는 엣지 케이스, 정밀한 Given-When-Then 인수 조건(Acceptance Criteria), 텍스트 기반 UI 와이어프레임이 완비된 '기능 명세서(SRS)'로 신속하게 구체화합니다.

1. 단계 목적 및 대상 페르소나 ​

  • 주요 담당자 (Persona): 제품 책임자(PO), 비즈니스 기획자, 도메인 분석가
  • 협업 대상: 수석 개발자(Lead Dev), UI/UX 디자이너
  • 목표 소요 시간: 기능당 30분 ~ 1시간 이내
  • 사용 도구: Claude 3.7 Sonnet / ChatGPT o3 / Cursor Chat / 사내 RAG 지식 허브

2. 단계 시작 전제조건 (Definition of Ready - DoR) ​

본 단계를 시작하기 전에 아래 사항이 준비되어 있어야 합니다:

  • [ ] 해결하고자 하는 핵심 비즈니스 문제 또는 고객의 페인포인트(Pain-point) 1문장 정의
  • [ ] 해당 기능이 속한 비즈니스 도메인 식별 (예: 주문, 결제, 회원, 정산, CMS 등)
  • [ ] 사내 기존 용어집 또는 관련 화면/기능의 레퍼런스 식별

3. 실전 수행 4단계 워크플로우 ​

Step 1: 한 줄 비즈니스 의도 입력 (Core Intent Ingestion) ​

기획자는 복잡한 서식 대신 핵심 의도와 목적만을 AI에게 입력합니다.

"우리 쇼핑몰에 연말 프로모션 쿠폰을 적용하려 해. 회원이 장바구니에서 보유 쿠폰 중 1개를 골라 할인받는 기능을 기획해줘."

Step 2: AI의 엣지 케이스 역질문 및 사각지대 발굴 (Blind Spot Discovery) ​

AI에게 사전에 정의된 도메인 규칙을 바탕으로 기획자가 미처 생각하지 못한 기술적·비즈니스적 예외 상황을 5가지 이상 역질문하도록 유도합니다.

  • 예: "쿠폰 할인 금액이 장바구니 총액보다 큰 경우 잔액은 소멸되나요, 마이너스 결제가 차단되나요?"
  • 예: "동일한 주문 건에 대해 결제 도중 취소하면 쿠폰은 즉시 복구되어야 하나요?"

Step 3: Given-When-Then 형식의 인수 조건(Acceptance Criteria) 도출 ​

확정된 답변을 토대로 기획자, 개발자, QA가 공통으로 이해할 수 있는 BDD(Behavior-Driven Development) 형식의 인수 조건을 작성합니다.

Step 4: 마크다운 기능 명세서(SRS) 및 UI 레이아웃 확정 ​

입출력 데이터 항목, 유효성 검증 규칙, 텍스트 와이어프레임을 포함한 마크다운 문서를 확정하고 Jira 티켓 본문에 첨부합니다.

4. 즉시 복사 가능한 실전 프롬프트 레시피 (Copy-Paste) ​

📌 프롬프트 1: 엣지 케이스 역질문 유도 (기획 결함 선제 예방) ​

markdown
[Role] 당신은 10년 차 IT 서비스 전문 수석 PO(Product Owner)이자 도메인 분석가입니다.
[Context] 전자상거래 플랫폼에서 아래 신규 기능의 요구사항을 정의하려고 합니다.
[Draft Idea]
"{{기획하고자 하는 기능의 핵심 아이디어를 2~3줄로 입력하세요. 예: 회원이 장바구니에서 쿠폰을 1개 선택하여 상품 총액에서 할인받는 기능}}"

[Task]
위 아이디어를 바탕으로, 개발 착수 전 기획 단계에서 반드시 결정해야 하는 비즈니스 예외 상황 및 엣지 케이스(Edge Cases) 5가지를 질문 형식으로 제시해 주세요.
- 결제/취소/환불 시나리오
- 최소/최대 조건 및 유효기간 만료 시점
- 동시성(중복 사용 시도) 및 보안 취약점
- 다른 혜택(적립금, 제휴 할인)과의 중복 적용 여부

📌 프롬프트 2: Given-When-Then 인수 조건 자동 도출 ​

markdown
[Role] 당신은 BDD(행동 주도 개발) 요구사항 분석 전문가입니다.
[Context] 아래의 기능 개요와 결정 사항을 바탕으로 QA 테스트가 가능한 Acceptance Criteria를 작성하세요.
[Feature Overview]
- 기능명: {{기능명}}
- 주요 규칙: {{Step 2에서 결정한 핵심 정책들}}

[Output Format]
각 사용자 시나리오별로 아래 형식을 엄격히 준수하세요:
- 시나리오 1: [정상 케이스 명칭]
  - Given (사전 조건):
  - When (사용자 행동):
  - Then (시스템 반응 및 결과):
- 시나리오 2: [예외 케이스 - 유효하지 않은 입력]
- 시나리오 3: [예외 케이스 - 잔액/재고 부족 또는 만료]
- 시나리오 4: [동시성 및 트랜잭션 오류 처리]

📌 프롬프트 3: 마크다운 기능 명세서 & 텍스트 와이어프레임 생성 ​

markdown
[Role] 기술 문서 작성을 전담하는 테크니컬 라이터 겸 서비스 기획자입니다.
[Input Data]
{{앞서 확정된 사용자 스토리 및 인수 조건 내용}}

[Instructions]
개발팀과 디자이너가 즉시 참조할 수 있도록 아래 마크다운 서식으로 SRS(Software Requirements Specification)를 완성해 주세요:
1. 기능 개요 및 비즈니스 KPI 목표
2. 화면 레이아웃 와이어프레임 (Markdown Table 또는 ASCII Art)
3. 화면 필드 정의 및 유효성 검증 규칙 표 (필드명, 타입, 필수여부, 오류메시지)
4. 백엔드 연동에 필요한 데이터 속성 목록

5. 자주 발생하는 AI 실수 및 안티패턴 (Pitfalls) ​

실수 유형 (Pitfall)AI의 흔한 실수 양상실무 해결책 (Countermeasure)
모호한 형용사 남발"빠르게 로딩된다", "적절한 오류 메시지를 보여준다" 등 측정 불가한 표현 생성프롬프트에 "모든 성공 기준은 수치(200ms 이내) 또는 고유 에러 코드(ERR_COUPON_EXPIRED)로 명시할 것"을 강제.
개발 기술 종속적 서술기획 단계인데 "Redis에 저장하고 Kafka로 토픽을 발행한다" 등 특정 인프라를 강제함프롬프트에 "인프라 구현 방식이 아닌 '사용자 관점의 비즈니스 행동과 결과'에만 집중하여 작성할 것"을 명시.
비기능 요구사항 누락기능 흐름만 명시하고 동시 접속 트래픽, 개인정보 마스킹, 다국어 처리 누락프롬프트에 "보안(PII), 동시성, 다국어 처리 항목을 필수 섹션으로 포함할 것"을 요구.

6. 단계 완료 판정 체크리스트 (Definition of Done - DoD) ​

다음 단계인 [02단계: 아키텍처 및 스펙 설계]로 넘어가기 위해 아래 항목을 확인합니다:

  • [ ] 기능의 핵심 사용자 스토리와 BDD(Given-When-Then) 인수 조건이 작성되었는가?
  • [ ] 최소 3개 이상의 비정상 엣지 케이스(만료, 잔액 부족, 중복 호출)가 정의되었는가?
  • [ ] 사용자에게 노출될 에러 메시지 문구가 명시적으로 확정되었는가?
  • [ ] 기획자(PO)와 개발 리드가 기능 명세 마크다운 문서에 상호 서명(또는 Jira 승인)하였는가?
