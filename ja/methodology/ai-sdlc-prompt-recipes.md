## 1. 企画および要件分析 (企画担当 / PO) {#1-planning-and-requirements}

### プロンプト 1.1: 例外ケースおよび仕様漏れの洗い出し
```markdown
[役割] IT サービスシニアプランナー兼ビジネスアナリスト
[機能名] {{機能名（例: カートクーポン適用機能）}}
[基本説明] {{機能に関する基本説明 2〜3行}}

[依頼事項]
本機能の開発に着手する前に、企画段階で事前に決定しておくべき技術的・ビジネス的な例外ケースを 5 つ質問形式で提示してください。
1. 決済 / キャンセル / 返金時のポリシー
2. 最小注文金額および最大割引金額の境界条件
3. 有効期限切れおよび複数端末での重複適用試行
4. 他の割引 (ポイント、提携カード) との併用ルール
```

### プロンプト 1.2: 状況別完了基準 (受け入れ条件) の作成
```markdown
[役割] 要件分析およびテスト設計の専門家
[コンテキスト]
- 対象機能: {{機能名}}
- 確定ポリシー: {{決定されたポリシー内容}}

[依頼事項]
QA テストが可能な完了基準 (Acceptance Criteria) を作成してください。
- シナリオ 1: 正常フロー (Happy Path)
- シナリオ 2: 入力値のバリデーション失敗 (Validation Error)
- シナリオ 3: 残高 / 在庫不足またはビジネス上限超過
- シナリオ 4: ネットワークタイムアウトまたは同時リクエスト競合
```

## 2. アーキテクチャおよびデータベース設計 (アーキテクト / DBA) {#2-architecture-and-database}

### プロンプト 2.1: PostgreSQL 18.6 標準 DDL の生成
```markdown
[役割] シニアデータベースアーキテクト
[データベース] PostgreSQL 18.6
[ドメイン] {{ドメイン名（例: shop_coupon）}}
[要件] {{機能仕様書の内容}}

[作成ルール]
1. テーブル名は小文字のスネークケース ({{ドメイン_エンティティ}}) で記述してください。
2. 主キー id は BIGINT 標準を適用してください。
3. 監査カラム (created_at, updated_at, created_by, updated_by, del_flag) を含めてください。
4. 頻繁に検索されるカラムには明示的なインデックス (INDEX) を付与してください。
5. 一時的な競合回避構文 (`ON CONFLICT DO NOTHING` 等) ではなく、一意性が検証された純粋な CREATE TABLE および INSERT 構文で記述してください。

[出力形式]
- Mermaid テーブル関連図
- 02_schema_domain.sql DDL スクリプト (テーブル、インデックス、コメント)
```

### プロンプト 2.2: 標準 REST API 仕様および OpenAPI 定義
```markdown
[役割] RESTful API 設計の専門家
[対象エンドポイント] {{リソースパス（例: /api/v1/shop/cart/coupon）}}
[データモデル] {{関連テーブルのカラム情報}}

[作成ルール]
1. 単一マッピング原則: 1 つの固有 URL のみを割り当ててください。
2. パスは必ず `/api/v1/{ドメイン}/{リソース}` 形式を遵守してください。
3. 共通レスポンス構造 (CommonResult: code, message, result, timestamp) を適用してください。

[出力形式]
1. API エンドポイント一覧表 (メソッド、URL、説明、権限)
2. 成功および失敗パターン別の JSON レスポンス例
3. OpenAPI 3.0 YAML 仕様スニペット
```

## 3. バックエンド Java Spring Boot 実装 (バックエンド開発者) {#3-backend-spring-boot}

### プロンプト 3.1: Lombok 適用および標準サービスの実装
```markdown
[役割] シニア Spring Boot 開発者
[技術スタック] Java 25, Spring Boot 4.0, PostgreSQL 18.6
[実装対象] {{実装する機能（例: クーポン適用ビジネスロジック）}}
[先行仕様] {{確定した DDL および API 仕様}}

[作成ルール]
1. Project Lombok の適用:
   - @Autowired フィールドインジェクションの代わりに private final フィールドと @RequiredArgsConstructor コンストラクタインジェクションを使用してください。
   - ロギングには @Slf4j を使用してください。
   - DTO には @Getter, @Builder, @NoArgsConstructor, @AllArgsConstructor を適用してください。
2. コントローラーのマッピングは単一標準 URL (`/api/v1/...`) のみを使用してください。
3. 単純な参照には @Transactional(readOnly = true)、データ更新メソッドには @Transactional を適用してください。
4. 一時的なダミーリターン (return null 等) ではなく、実際のデータアクセス層と連携する完成されたコードで記述してください。
```

## 4. フロントエンド Vue 3 およびモーダル分離 (フロントエンド開発者) {#4-frontend-vue3-modal}

### プロンプト 4.1: BasicModal 独立ポップアップコンポーネントの作成
```markdown
[役割] Vue 3 および TypeScript フロントエンド開発者
[実装対象] {{モーダル機能の説明（例: 保有クーポン選択および適用モーダル）}}
[連携 API] {{バックエンド API URL およびリクエスト/レスポンス JSON}}

[作成ルール]
1. フレームワーク標準モーダルである BasicModal を使用してください。
2. 親画面にインラインで記述せず、components/CouponApplyModal.vue として独立分離してください。
3. モーダル内部に適切なパディング (p-4) を設定してください。
4. 単なる空画面ではなく、テーブル、ラジオボタン選択、割引金額プレビューなどの実質的な画面要素を含めてください。
5. interface Props および Emits(open, success, confirm) を明確に宣言してください。
```

## 5. テストおよび品質検証 (QA エンジニア) {#5-testing-and-qa}

### プロンプト 5.1: JUnit 5 例外ケース単体テストの作成
```markdown
[役割] シニア QA エンジニア
[テスト対象コード]
{{テスト対象の Service または Controller ソースコード}}
[完了基準]
{{状況-行動-結果のシナリオ}}

[作成ルール]
1. 正常動作以外に、少なくとも 3 つ以上の異常例外ケースを個別の @Test として作成してください:
   - 有効期限切れの試行、残高不足の試行、重複同時呼び出しの試行
2. AssertJ (assertThat, assertThatThrownBy) を使用してアサーションを記述してください。
3. アサーションのない空テストは避け、各テストにつき 2 つ以上の結果検証を行ってください。
4. @DisplayName に日本語でテスト目的を明確に記載してください。
```

## 6. エラー解決および自動修正 (デバッグ / トラブルシューティング) {#6-debugging-and-troubleshooting}

### プロンプト 6.1: ビルドエラーおよびテスト失敗の自動修正
```markdown
[役割] ソフトウェアデバッグおよびエラー修正エージェント
[コンテキスト] ビルド中にコンパイルエラーまたはテストエラーが発生しました。
[エラーログ]
{{エラーログのスタックトレース内容}}

[エラー発生ソースコード]
{{該当ファイルのソースコード全文}}

[作成ルール]
1. 原因分析: エラーの原因を 2 行以内で要約してください。
2. 副作用チェック: 修正時に発生し得る影響範囲を確認してください。
3. 置換コード: 該当ソースコード全体をそのまま置き換えられる形式で記述してください。
   - [注意] エラー解消のためにビジネスバリデーション文 (if 文) を勝手に削除しないでください。
   - [注意] メソッド内部を空欄 (// TODO) のままにしないでください。
```

### プロンプト 6.2: クエリ性能ボトルネックの改善 (N+1 問題など)
```markdown
[役割] データベースクエリチューニング専門家
[コンテキスト] サービス実行中に特定の API でスロークエリまたは N+1 問題が発生しました。
[対象コードまたはクエリログ]
{{Mapper XML または JPA エンティティ / リポジトリコード}}

[依頼事項]
1. クエリボトルネックが発生する原因を説明してください。
2. JOIN クエリやバッチ取得など、最適なチューニング方針を提示してください。
3. チューニング前後の想定クエリ実行回数と性能差を比較してください。
```

## 7. コードレビューおよびデプロイサマリー (レビュアー / 運用担当) {#7-code-review-and-release}

### プロンプト 7.1: Git Diff ベースの PR 本文整理
```markdown
[役割] リリースエンジニアリング テクニカルライター
[Git Diff 内容]
{{git diff 内容を貼り付け}}

[記載項目]
1. 作業概要 (背景および目的)
2. 主な変更点 (バックエンド、フロントエンド、DB スキーマ)
3. 注意事項およびリスク確認 (既存機能への影響有無)
4. テスト検証結果の要約
```

### プロンプト 7.2: アーキテクチャ観点のコードレビューコメント作成
```markdown
[役割] シニアシステムアーキテクト兼セキュリティ監査担当
[レビュー対象コード]
{{レビュー対象の変更ソースコード}}

[チェック基準]
1. 並行性の欠陥およびトランザクション境界の設定有無
2. セキュリティ脆弱性 (SQL インジェクション、機密情報の露出、権限検証の漏れ)
3. 社内標準の遵守 (Lombok 適用、単一標準 URL、モーダルコンポーネント分離)
4. 可読性および単一責任の原則

[出力形式]
行ごとの具体的な改善提案 (改善前後のコード例を含む) および総合判定コメント。
```
