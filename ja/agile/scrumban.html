スクランバン（Scrumban） ​

一言まとめ: スクランバンは、スクラムの構造（役割／ミーティング／バックログの概念）とカンバンのフロー重視・WIP制限（Work In Progress制限）を組み合わせたプロセスです。スプリントの厳格さではなく フロー（Flow） と プル（Pull） を重視しつつ、必要な箇所にはスクラム式のイベント（計画・振り返り）を維持します。

ご案内: 事業全周期の受注、契約、125種の単一標準成果物の納品およびAI開発ライフサイクル（AI-SDLC）については、エムパシー事業・開発メソドロジー総合ポータルをご参照ください。

概要・定義 ​

スクランバン（Scrumban） は、ソフトウェア開発および知識労働チームが柔軟にワークフローを管理できるように設計されたハイブリッド型プロセスです。

  • スクラム: 反復（スプリント）、固定されたイベント（スプリントプランニング・レビュー・レトロスペクティブ）、明確な役割
  • カンバン: 視覚的なボード、WIP制限、プルベースの作業、継続的改善 スクランバンは上記2つのアプローチの利点を取り入れながら、現実的なフローの改善に焦点を当てます。

どのような場合にスクランバンを使うべきか？ ​

  • 従来 スクラム を使用しているが、頻繁な変更（緊急リクエスト）が多く、スプリント単位でまとめるのが難しい場合。
  • カンバン でフローを回しているものの、バックログ管理・優先順位付け・定期的な振り返りといった規律が必要なチーム。
  • 保守・運用・サポート（運用タスクと新機能開発が混在する）チーム。
  • 予測よりも 継続的デリバリー（Continuous Delivery） とフローの最適化をより重視する場合。

コアコンセプト ​

  1. Pullシステム: 作業はチームが処理可能なタイミングでのみ開始します（次の列へ引き込む）。
  2. WIP（進行中の作業）制限: 同時に進行する作業数を制限し、マルチタスクを減らして完了を促進します。
  3. 視覚化されたボード: 作業のステータスを明確に示し、ボトルネックを即座に確認できます。
  4. 定期的なリフィル（Replenishment）／プランニング: 必要なタイミングでのみバックログから作業を補充します（定期的、またはしきい値到達時）。
  5. 測定と改善: サイクルタイム、リードタイム、スループットなどの指標を用いてフローを改善します。
  6. 明示的なポリシー（Explicit Policies）: 列の移行条件、優先順位ルール、Definition of Ready/Doneを明文化します。

スクラム vs カンバン vs スクランバン ​

項目スクラムカンバンスクランバン
反復（スプリント）あり（固定長）なし（継続的フロー）選択的／短いイテレーションの併用
WIP制限暗黙的（スプリント範囲）明示的明示的（中核）
計画方式スプリントプランニングリフィル／プルベースリフィル ＋ 必要に応じたプランニング
役割PO/SM/Dev柔軟（役割なし）PO ＋ Flow Manager（またはSMの役割を維持）
目標コミット（スプリント目標）フロー最適化フロー最適化 ＋ 優先順位管理

役割と責任 ​

  • Product Owner（PO）: バックログの優先順位付け、ステークホルダーとの調整、ビジネス価値の定義
  • Flow Manager（またはScrum Masterの役割を維持）: フローのモニタリング、ボトルネック解消の支援、プロセス改善の促進
  • チーム（開発者／テスターなど）: 定義されたポリシーの遵守、WIP上限内でのプル方式による作業の開始／完了
  • Stakeholders: 要件・フィードバックの提供、レビューへの参加（必要時）

役割はチームの状況に合わせて柔軟に調整してください。重要なのは フロー管理の責任 が明確であることです。

主要アーティファクト・ツール ​

  • カンバンボード（物理またはデジタル）— 列とWIP上限を含む
  • バックログ（優先順位付きリスト） — プル待ち状態の作業候補
  • 明示的なポリシー（Explicit policies） — 列の移行ルール、定義（Ready/Done）
  • サービスクラス（Classes of Service） — 緊急／固定日／標準などの優先度タイプ
  • メトリクスダッシュボード: サイクルタイム、リードタイム、スループット、CFD（累積フロー図）

ボードレイアウト ​

基本的なスクランバンボード（例）：

列説明推奨WIP上限
Backlog優先順位が付けられたすべての作業—
Ready開始可能な作業（Doingへ移動可能な状態）—
Doing / In Progress実際に作業中3
Code Reviewレビュー待ち2
TestingQA／検証2
Done完了—

簡易ASCIIボード:

Backlog -> Ready -> [Doing (WIP 3)] -> Code Review (WIP 2) -> Testing (WIP 2) -> Done

ワークフロールールの例 ​

text
Policy: Pull条件（Doing列への移動）
- カードがReady列にあり、かつDoing列のWIP < WIP上限
- 該当作業の「Definition of Ready」を満たしている（要件／テストケース／デザインなど）
- 必要なリソース（テスター／レビュアー）の稼働可否を確認済み

Policy: Definition of Done（完了の定義）
- コードがマージされ、ビルドが成功している
- 自動／手動テストに合格している
- デプロイ（またはQA引き継ぎ）のドキュメント化が完了している

Classes of Serviceの例

  • Expedite: 即時処理（作業優先度最上位、WIP例外を許容）
  • Fixed Date: 特定の日付が必要 — スケジュール監視が必要
  • Standard: 通常リクエスト
  • Intangible: 技術的負債などの長期的価値

イベントと推奨周期 ​

  • Daily Stand-up（毎日、10〜15分）: フロー中心で実施（何をしているかよりもボトルネック／ブロッカーの共有）
  • Replenishment / Backlog Refinement（週1回または必要時）: Ready列の補充 — 優先順位の再整理
  • Planning（必要時）: 大きな作業（エピック）の分割または代替計画 — 短時間で実施
  • Retrospective（2〜4週間周期）: プロセス改善、WIP上限の調整検討
  • Service Delivery Review / Ops Review（月次）: SLA・SLE・指標のレビュー

スクラムのようにすべての会議を厳格に固定する必要はありません。フローを妨げるポイント が見えたときに会議を導入してください。

見積り・計画方法 ​

  • ストーリーポイントの維持: スクラムから移行するチームに適しています。スループット対比の予測に有利です。
  • No Estimates（見積り省略）: カードの単純カウント ＋ サイクルタイム／スループットによる予測。
  • バケット（期間ベース）計画: 月ごとに完了可能な作業量（スループット）を基準にリフィルします。
  • 推奨: 重い見積り作業を減らし、実績データ（サイクルタイム、スループット） に基づいて予測してください。

主要メトリクス（定義・活用） ​

  • リードタイム（Lead Time） = カードがバックログ登録（または作成）された時点 → 完了時点
  • サイクルタイム（Cycle Time） = 作業開始（Doing） → 完了
  • スループット（Throughput） = 特定期間内に完了したカード数
  • WIP（平均進行中作業数）
  • Cumulative Flow Diagram（CFD）: 各列の累積領域によりボトルネック・フローの変化を可視化
  • サービスレベル期待値（SLE）: 例：85%の作業が10日以内に完了すること

参考活用法

  • Little’s Law: WIP = Throughput × Cycle Time（平均値を使用）— 予測および限界把握に有用
  • 目標: サイクルタイムの安定化 → 予測可能性の向上

スクラムからスクランバンへの移行 ​

  1. 現在のプロセスのマッピング: どのような仕事がどのように流れているかを可視化
  2. ボードの構成: 最小限の列から開始（Ready → Doing → QA → Done）
  3. WIP上限の設定: 保守的に開始（例：Doing = チームメンバー数 ÷ 2）
  4. リフィルルールの策定: いつBacklogからReadyへ補充するかを決定（週次／しきい値）
  5. データ収集: サイクルタイム・スループットの収集（2〜4週間）
  6. 調整の反復: レトロスペクティブでWIP・列・ポリシーを調整

カンバン／スクランバン導入チェックリスト ​

  • [ ] ボードがチームの実態を反映しているか？
  • [ ] WIP上限が設定されており、全員が理解しているか？
  • [ ] Definition of Ready/Doneがドキュメント化されているか？
  • [ ] Replenishmentの周期（またはルール）が決まっているか？
  • [ ] Daily stand-upでボトルネック中心の議論が行われているか？
  • [ ] サイクルタイム・スループット・CFDを収集し分析しているか？
  • [ ] サービスクラスとポリシーが定義されているか？
  • [ ] 定期的なレトロスペクティブでプロセス変更が反映されているか？

実践のヒント＆ベストプラクティス ​

  • 小さく始める: ボードとWIP上限を小さく作り、素早くフィードバックを得ます。
  • Stop starting — start finishing: 新しい作業を始めることよりも、進行中の仕事を終わらせる文化を根付かせます。
  • WIP違反時のチーム規律: 即座に議論します（なぜ違反したのか、ボトルネックの原因を把握）。
  • 視覚的シグナル: ブロッカー／緊急カードは別の色やステッカーで表示します。
  • ポリシーはドキュメント化: 「いつカードを移動させるか」を明確に記述しておきます。
  • 自動化: CI/CD、自動テストによってサイクルタイムを短縮します。
  • データに基づく意思決定: 見積りよりも実際のサイクルタイム／スループットで計画します。

よくある失敗 ​

  • WIP上限を設定しただけで守らないケース
  • スクラムのイベントをそのまま維持しながらWIP・プルの概念を無視するケース
  • クラスを作成したものの基準なしに使用するケース（優先順位の混乱）
  • 指標を収集せず「感覚」だけで意思決定するケース
  • 列や細分化が多すぎてボードが複雑化するケース

テンプレート：Replenishmentミーティング（簡易アジェンダ） ​

  1. 先週完了した作業（簡易レビュー） — 5分
  2. Ready列の状態確認（優先順位の再整列） — 10〜20分
  3. WIP上限に対する現在の稼働リソース確認 — 5分
  4. 新規作業のPull決定（優先順位順に補充） — 10〜20分
  5. Blocker／リスク要因の共有 — 5分

FAQ ​

Q. スプリントは完全になくなりますか？ A. チームが希望すれば、短いイテレーション（例：2週間）を維持しながらスクランバン原則を適用できます。重要なのはフローの改善です。

Q. ストーリーポイントは使い続けるべきですか？ A. 必ずしもそうする必要はありません。スループットとサイクルタイムで予測する方法も多く使われています。チーム文化や報告の必要性に応じて決定してください。

Q. WIP上限はどのように決めますか？ A. 保守的に始めます（チームメンバー数基準、または過去のスループットから推定）。上限を守りながら段階的に調整します。

適用例 ​

  • チームメンバー5名 → Doing WIP = 3（同時作業制限）
  • Replenishment：週1回（月曜日）
  • Retrospective：2週間ごと（オンライン・オフライン併用）
  • 指標：週単位のスループット ＋ 4週間の累積サイクルタイムの観察

まとめ — 導入ガイド ​

  1. ボードを作成し、
  2. WIP上限を定め、
  3. プル（Pull）ルールとDefinitionをドキュメント化 したうえで、
  4. データ（サイクルタイム・スループット）を2〜4週間収集 し、レトロスペクティブで調整 してください。
