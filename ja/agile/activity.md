# スクラムバン フェーズ別Activityガイド

| フェーズ                                      | 主なActivity                                                                        | 詳細説明                                                                                                                                                                                                           |
| ----------------------------------------- | ----------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **1. Backlog**                            | - 新規アイデア・リクエストの収集<br>- バックログアイテムの記録<br>- サービスクラス（Class of Service）の指定 | すべての作業の出発点です。<br>ビジネス要求、バグ、技術的負債などを**Product Owner**やチームが記録します。<br>各カードに**優先度**と**作業タイプ（緊急・期日固定・標準・無形）**を指定します。<br>このフェーズでは、まだ着手の準備が整っていない状態です。 |
| **2. Ready**                              | - Definition of Ready (DoR) の確認<br>- 作業の分解（必要時）<br>- 担当者未指定      | 作業をすぐ開始できるよう詳細内容が整った状態です。<br>DoR基準（要件の明確化、デザイン・リソースの確保、テスト条件の定義など）を満たす必要があります。<br>通常、**Replenishmentミーティング**でBacklogからReadyへ移動します。 |
| **3. Doing / In Progress**                | - 作業開始（Pull）<br>- 進行状況のアップデート<br>- ブロッカーの明示                | チームメンバーがWIP上限内でReadyからPullして作業を開始します。<br>作業中に発生した**ボトルネック・ブロッカー**は、ボード上で視覚的に表示します（赤いラベル、アイコンなど）。<br>デイリースタンドアップでステータスを共有します。 |
| **4. Review (Code Review / Peer Review)** | - コードレビュー・ドキュメントレビューの実施<br>- フィードバックの反映                | 開発が完了した作業はReviewカラムへ移動します。<br>指定されたレビュアーがコード品質や標準への準拠を確認します。<br>レビューのフィードバックがある場合はDoingへ戻すか、修正後に再度Reviewフェーズへ進めます。 |
| **5. Testing / QA**                       | - 機能テスト<br>- バグレポートの作成および修正                                      | QAまたはチームメンバーがテストを実施します。<br>自動テストと手動テストを併用できます。<br>バグが見つかった場合は該当カードに記録し、修正後に再検証を行います。 |
| **6. Done**                               | - Definition of Done (DoD) の充足確認<br>- ドキュメント・リリースノートの更新<br>- デプロイ完了 | すべての品質基準を満たし、デプロイまで完了した状態です。<br>リリースノートやユーザーマニュアルなどのドキュメント化を含みます。<br>カードに完了日を記録します（サイクルタイム分析に活用）。 |

## 各フェーズのActivityフロー可視化

```
[Backlog]
  ↓ (Replenishmentミーティング)
[Ready]
  ↓ (Pull & WIPチェック)
[Doing]
  ↓ (開発完了)
[Review]
  ↓ (レビュー承認)
[Testing]
  ↓ (品質検証完了)
[Done]
```

## フェーズ別運用ヒント

### 1. Backlog

- **優先度基準の明確化**: 緊急度、ビジネス価値、期限、リスクに基づく判断
- **カードサイズの標準化**: 大きすぎる場合はReadyへ移す前に分割
- **定期的な整理**: 古いカードや不要になったカードは破棄

### 2. Ready

- **作業着手可能条件（DoR）チェックリスト例**

  - 要件が明確である
  - デザイン・データ・リソースが確保されている
  - テスト条件が定義されている
  - 見積もり作業時間・スコープが確認されている

### 3. Doing

- **Stop Starting, Start Finishing** ルールの維持
- ボトルネック発生時は即座に解決策を協議
- マルチタスクの最小化

### 4. Review

- コードレビュー基準の定義（例：コードスタイル、パフォーマンス、セキュリティ、テストの有無）
- レビュー待ち時間を短縮するための通知システムの活用

### 5. Testing

- 自動テストと手動テストの併用
- バグ発生時は同一カード上で修正後に再検証
- テスト失敗時はWIP超過の例外を許容可能

### 6. Done

- 完了後にカードへ**サイクルタイムを記録**
- リリースふりかえり時に完了カードをレビュー
- データ分析用タグ（バグ、新機能など）を付与

## フェーズ別主要指標

| フェーズ            | 主要指標                   | 活用目的                 |
| --------------- | -------------------------- | ------------------------ |
| Backlog → Ready | リードタイム（要求\~準備完了） | 準備遅延の原因把握       |
| Ready → Doing   | Pull頻度                   | チームの処理能力の把握   |
| Doing           | 平均WIP、ブロッカー比率    | ボトルネック管理         |
| Review          | レビュー待ち時間           | 品質と速度のバランス調整 |
| Testing         | 欠陥率、手戻り率           | QA効率性の評価           |
| Done            | サイクルタイム、スループット | 予測可能性の向上         |

---

このように整理することで、**スクラムバンを導入したチームが各フェーズで何を実施すべきか**が明確になり、
**メトリクスに基づく継続的改善活動**もあわせて推進できます。
