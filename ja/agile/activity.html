スクラムバン フェーズ別Activityガイド ​

フェーズ主なActivity詳細説明
1. Backlog- 新規アイデア・リクエストの収集
- バックログアイテムの記録
- サービスクラス（Class of Service）の指定		すべての作業の出発点です。
ビジネス要求、バグ、技術的負債などをProduct Ownerやチームが記録します。
各カードに優先度と作業タイプ（緊急・期日固定・標準・無形）を指定します。
このフェーズでは、まだ着手の準備が整っていない状態です。
2. Ready- Definition of Ready (DoR) の確認
- 作業の分解（必要時）
- 担当者未指定		作業をすぐ開始できるよう詳細内容が整った状態です。
DoR基準（要件の明確化、デザイン・リソースの確保、テスト条件の定義など）を満たす必要があります。
通常、ReplenishmentミーティングでBacklogからReadyへ移動します。
3. Doing / In Progress- 作業開始（Pull）
- 進行状況のアップデート
- ブロッカーの明示		チームメンバーがWIP上限内でReadyからPullして作業を開始します。
作業中に発生したボトルネック・ブロッカーは、ボード上で視覚的に表示します（赤いラベル、アイコンなど）。
デイリースタンドアップでステータスを共有します。
4. Review (Code Review / Peer Review)- コードレビュー・ドキュメントレビューの実施
- フィードバックの反映		開発が完了した作業はReviewカラムへ移動します。
指定されたレビュアーがコード品質や標準への準拠を確認します。
レビューのフィードバックがある場合はDoingへ戻すか、修正後に再度Reviewフェーズへ進めます。
5. Testing / QA- 機能テスト
- バグレポートの作成および修正		QAまたはチームメンバーがテストを実施します。
自動テストと手動テストを併用できます。
バグが見つかった場合は該当カードに記録し、修正後に再検証を行います。
6. Done- Definition of Done (DoD) の充足確認
- ドキュメント・リリースノートの更新
- デプロイ完了		すべての品質基準を満たし、デプロイまで完了した状態です。
リリースノートやユーザーマニュアルなどのドキュメント化を含みます。
カードに完了日を記録します（サイクルタイム分析に活用）。

フェーズ別運用ヒント ​

1. Backlog ​

  • 優先度基準の明確化: 緊急度、ビジネス価値、期限、リスクに基づく判断
  • カードサイズの標準化: 大きすぎる場合はReadyへ移す前に分割
  • 定期的な整理: 古いカードや不要になったカードは破棄

2. Ready ​

  • 作業着手可能条件（DoR）チェックリスト例

    • 要件が明確である
    • デザイン・データ・リソースが確保されている
    • テスト条件が定義されている
    • 見積もり作業時間・スコープが確認されている

3. Doing ​

  • Stop Starting, Start Finishing ルールの維持
  • ボトルネック発生時は即座に解決策を協議
  • マルチタスクの最小化

4. Review ​

  • コードレビュー基準の定義（例：コードスタイル、パフォーマンス、セキュリティ、テストの有無）
  • レビュー待ち時間を短縮するための通知システムの活用

5. Testing ​

  • 自動テストと手動テストの併用
  • バグ発生時は同一カード上で修正後に再検証
  • テスト失敗時はWIP超過の例外を許容可能

6. Done ​

  • 完了後にカードへサイクルタイムを記録
  • リリースふりかえり時に完了カードをレビュー
  • データ分析用タグ（バグ、新機能など）を付与

フェーズ別主要指標 ​

フェーズ主要指標活用目的
Backlog → Readyリードタイム（要求~準備完了）準備遅延の原因把握
Ready → DoingPull頻度チームの処理能力の把握
Doing平均WIP、ブロッカー比率ボトルネック管理
Reviewレビュー待ち時間品質と速度のバランス調整
Testing欠陥率、手戻り率QA効率性の評価
Doneサイクルタイム、スループット予測可能性の向上

このように整理することで、スクラムバンを導入したチームが各フェーズで何を実施すべきかが明確になり、 メトリクスに基づく継続的改善活動もあわせて推進できます。
